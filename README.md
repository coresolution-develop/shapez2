# shapez 2 도우미

shapez 2의 목표 도형 코드를 넣으면 **채굴 → 절단 → 회전 → 도색 → 적층** 가공 순서를 계산해 주는 웹 앱입니다.

핵심은 게임 규칙을 그대로 옮긴 시뮬레이터입니다. 솔버가 내놓는 모든 계획은 이 시뮬레이터로 한 단계씩 실행해서 **결과가 목표 도형과 정확히 일치하는 것만** 화면에 표시합니다. 즉, 틀린 답을 그럴듯하게 보여주는 일이 없습니다.

## 실행

```bash
pnpm install
pnpm dev
```

| 명령 | 설명 |
|------|------|
| `pnpm dev` | 개발 서버 |
| `pnpm build` | 프로덕션 빌드 |
| `pnpm test` | 시뮬레이터 정합성 + 솔버 커버리지 테스트 |
| `pnpm lint` | ESLint |

## 구조

```

│   ├── operations.ts      # 10개 가공 연산 시뮬레이터
│   ├── plan.ts            # 가공 계획 DAG 자료구조
│   ├── solver.ts          # 역설계 솔버
│   ├── throughput.ts      # 건물 처리량 데이터 + 소요량 계산
│   ├── blueprint.ts       # 청사진 코드 디코더
│   ├── progression.ts     # 마일스톤·연구 해금 규칙
│   ├── namesKo.ts         # 게임의 한국어 명칭

│   ├── presets.json       # 게임 내 실제 목표 도형 1,387개
│   ├── progression.json   # 시나리오별 해금 순서
│   └── buildings.json     # 건물 126종·플랫폼 59종 메타데이터
├── components/shape-view.tsx          # 도형 SVG 렌더러
├── features/reverse-engineer/         # 역설계 + 처리량 화면
└── features/blueprint/                # 청사진 뷰어
```

## 진행도 반영

**"내 진행 상황"을 마일스톤으로 설정하면 그 시점에 지을 수 있는 건물로만 가공 순서를 짭니다.** 게임의 해금 순서를 그대로 따릅니다.

| 시점 | 해금 |
|------|------|
| M1 | 컨베이어 벨트, 미니 채굴기, 절반 파괴기, 시계 90° 회전기 |
| M2 | 결합기 |
| M5 | 색칠기 (1차색 R·G·B만) |
| M7 | 핀 누름기 |
| M8 | 색상 혼합기 → 2차색(C·M·Y)·흰색 |
| M10 | 결정체 생성기 |
| 연구포인트 | 절단기, 교환기, 반시계·180° 회전기, 굽은 결합기 |

절단기·교환기처럼 연구포인트로 따로 사는 건물은 별도로 체크할 수 있습니다.

못 만드는 도형은 그냥 실패하지 않고 **뭐가 없어서 안 되는지** 알려줍니다 — 예: `CrCrCrCr`을 M4에서 조회하면 "필요: 색칠기 (마일스톤 5 · Fluids & Painting)". 2차색을 요구하면 색상 혼합기를 짚어 줍니다.

## 옆에 띄워두고 쓰기

- **URL에 상태 저장** — 도형 코드·시나리오·진행도·목표 처리량이 전부 쿼리스트링에 들어갑니다. 북마크하거나 링크를 폰으로 보내면 그대로 열립니다. 링크 복사 버튼도 있습니다.
- **다크 모드** — 시스템 설정을 따르고 토글로 바꿀 수 있습니다.
- **즐겨찾기 · 최근 본 도형** — 브라우저에 저장돼서 다음에 열어도 남아 있습니다.
- **마일스톤 납품 도형 바로가기** — 진행도를 설정하면 그 마일스톤의 목표 도형이 썸네일로 뜨고, 누르면 바로 역설계합니다.

## 처리량 계산

가공 순서가 나오면 **목표 처리량(개/분)** 을 입력해서 각 단계에 건물이 몇 대 필요한지 계산합니다.

- 단계별 소요 건물 수와 실제 가동률(개/분)
- 건물 종류별 합계, 추출기 대수, 출력 벨트 줄 수
- 색상별 페인트 소요량(L/분)
- 속도 업그레이드 단계(50~150%)와 결합기 종류(일반/굽은형) 반영

계산은 계획 DAG를 역방향으로 훑으면서 각 노드의 요구량을 누적합니다. 절단기·교환기처럼 출력이 2개인 건물은 **한 대가 양쪽 출력을 담당**하므로 요구량의 최댓값으로 묶어 계산합니다(중복 계산 방지).

건물 속도는 100% 기준 처리량(개/분)에 업그레이드 배율을 곱합니다.

| 건물 | 100% 기준 | 건물 | 100% 기준 |
|------|-----------|------|-----------|
| 컨베이어 벨트 | 120 | 절단기 | 30 |
| 회전기 | 60 | 교환기 | 30 |
| 절반 파괴기 | 40 | 색칠기 | 30 (페인트 10L/개) |
| 핀 누름기 | 40 | 결합기 | 20 |
| 미니 채굴기 | 30 | 결정체 생성기 | 20 (페인트 20L/개) |

벨트 분배 손실이나 레인 배치는 반영하지 않은 이론값입니다.

## 청사진 뷰어

게임에서 복사한 청사진 코드(`SHAPEZ2-1-...$`)를 붙여넣으면 내용을 풀어서 보여줍니다. 주변 텍스트가 섞여 있어도 코드만 골라냅니다.

- 종류(건물/플랫폼), 게임 버전, 건물 수, 플랫폼 수
- 가로×세로 크기, 층 수, 회전을 반영한 점유 타일 수
- 건물 종류별 개수 (게임 내 영문 이름)
- 청사진 아이콘 (도형 아이콘은 그려서 표시)
- 층별 배치도 — 타일 하나가 한 칸, 운반/가공/유체/회로별로 색 구분

포맷은 `SHAPEZ2-<메이저버전>-<base64(gzip(JSON))>$` 입니다. gzip은 브라우저 내장 `DecompressionStream`/`CompressionStream`을 써서 외부 의존성이 없습니다.

메이저 버전 1과 5를 모두 읽습니다. 5에서 세 군데가 바뀌었습니다.

| | 버전 1 | 버전 5 |
|---|---|---|
| 끝부분 | `...==$` | `...==[{...}]_171$` |
| 배열 | `"Entries": [...]` | `"Entries": {"$values": [...]}` |
| 아이콘 | 압축 본문 안 | 뒤쪽 꼬리표 안 |

**청사진 인코더**도 있습니다. 생성한 청사진은 공식 파이썬 디코더가 위치·회전·레이어·아이콘·크기·비용까지 그대로 읽어냅니다.

## 건물 포트 (벨트 연결 위치)

게임 데이터에는 건물이 차지하는 타일만 있고 **입출력이 어느 면인지는 없습니다.** 그래서 추측하지 않고, 실제로 돌아가는 공장에서 **역산**했습니다.

벨트는 자기 로컬 +X로 이동하므로 기계를 향한 벨트는 입력, 기계에서 시작하는 벨트는 출력입니다. 여기에 "모든 인스턴스에서 점유된 면은 포트"라는 신호를 더합니다. 규칙: **로컬 -X 입력, +X 출력.**

| 건물 | 입력 | 출력 | 표본 |
|------|------|------|------|
| 절단기 | (-1,0) | (1,0) (1,-1) | 40 |
| 절단기(미러) | (-1,0) | (1,0) (1,1) | 8 |
| 결합기 | (-1,0) | (1,0) | 72 |
| 색칠기 | (-1,0) | (1,0) | 24 |
| 결정체 생성기 | (-1,0) | (1,0) | 36 |
| 회전기 | (-1,0) | (1,0) | 24 |
| 컨베이어 벨트 직진 | (-1,0) | (1,0) | 477 |
| 컨베이어 벨트 좌/우회전 | (-1,0) | (0,-1) / (0,1) | 82 / 75 |
| 병합기 2→1 | (-1,0) (0,-1) | (1,0) | 36 |
| 분배기 1→2 | (-1,0) | (1,0) (0,-1) | 19 |
| 분배기 T | (-1,0) | (0,-1) (0,1) | 28 |
| 벨트 포트 송/수신 | (-1,0) / — | — / (1,0) | 57 / 45 |

`portData.ts`의 모든 항목에는 **출처**(`fixture` = 저장소에 포함된 청사진에서 재역산 / `player-report` = 게임에서 직접 측정)와 **표본 수**가 붙어 있습니다. 테스트가 `fixture` 항목을 매번 다시 역산해서 표와 대조하므로, 손으로 적은 값이 슬쩍 섞일 수 없습니다.

**아직 모르는 것**은 일부러 비워 뒀습니다 — 반시계·180° 회전기, 절반 파괴기, 핀 누름기, 교환기, 굽은 결합기.

불완전한 것은 두 종류로 나눠 두었습니다.

- `partialBelts` — 벨트 포트가 덜 관측됨. **자동 배치 거부.** 결합기는 도형을 2개 받는데 입력이 1개만 잡혔습니다(나머지는 다른 층 리프트로 들어옴).
- `fluidUnknown` — 파이프 면만 모름. **배치는 허용**하고 "배관은 직접 연결하세요"라고 알립니다. 색칠기·결정체 생성기가 여기 해당합니다.

처음엔 이 둘을 뭉뚱그렸다가 색칠기까지 거부당해서 나눴습니다.

### 알게 된 것: 파이프는 양방향

처음엔 파이프도 벨트처럼 단방향으로 가정했는데, 그러니 유체 포트 송신기가 "출력만 있는 건물"로, 색상 혼합기가 "입력이 없는 건물"로 나왔습니다. shapez 2 파이프는 양방향이라 회전값이 흐름 방향을 뜻하지 않습니다. 지금은 유체 연결을 방향 없이 따로 기록합니다.

### 청사진 뷰어의 포트 분석

청사진을 붙여넣으면 그 안의 건물 포트를 분석해서 표로 보여주고, 결과를 복사할 수 있습니다. 새 기계의 기하를 확인하는 통로입니다 — 작동하는 공장을 붙여넣으면 쓰이는 면이 저절로 드러납니다.

## 청사진 생성

가공 순서가 **한 도형이 기계를 일렬로 통과하는 형태**면 실제로 붙여넣을 수 있는 청사진을 만들어 줍니다. 회전·도색·크리스탈, 그리고 마지막 단계의 절단까지 지원합니다.

배치는 확정된 포트 규칙(-X 입력, +X 출력)을 그대로 씁니다. 기계를 회전값 0으로 왼쪽에서 오른쪽으로 늘어놓고 사이사이에 벨트를 넣으면 배선이 저절로 맞습니다.

**게임에서 검증했습니다** — 생성한 청사진이 평지에 붙고, 벨트가 기계에 실제로 물립니다.

만들 수 없는 경우엔 이유를 말하고 거부합니다:

- 두 도형을 합치는 단계(적층·교환)가 있음
- 라인 중간에 절단이 있음(출력이 2개라 분기 배선 필요)
- 포트를 아직 모르는 기계를 씀(절반 파괴기·핀 누름기·교환기·굽은 결합기)

안 붙는 청사진을 만드는 것보다 거부하는 편이 낫다고 봤습니다.

몇 가지 실무적인 판단:

- **추출기는 넣지 않습니다.** 자원 패치 위에만 놓이는 건물이라 하나라도 포함되면 청사진 전체가 평지에 안 붙습니다. 직접 놓고 맨 앞 벨트에 연결하는 방식입니다.
- **배관은 생성하지 않습니다.** 색칠기·결정체 생성기의 파이프 면을 아직 특정하지 못했습니다. 벨트 배선은 정확하니 물감만 직접 연결하면 됩니다.

테스트는 생성한 청사진을 **다시 디코딩해서 각 건물의 출력이 다음 건물의 입력에 실제로 닿는지** 확인합니다. 배치만 맞고 배선이 틀린 경우를 잡기 위해서입니다.

## 용어

건물·색상 이름은 **게임의 한국어 번역을 그대로** 씁니다. 절단기, 결합기, 색칠기, 핀 누름기, 결정체 생성기처럼요 — 앱에서 읽는 이름과 게임에서 보는 이름이 달라서는 안 되니까요.

"스태커", "페인터" 같은 음차는 쓰지 않습니다. 테스트가 이런 표현이 다시 들어오는지 검사합니다.

## 데이터 출처

도형 규칙, 연산 정의, 프리셋 도형은 모두 공식 [`shapez2`](https://github.com/Loupau38/shapez2-python) 파이썬 패키지(게임 데이터 동봉)를 기준으로 했습니다. 추측한 규칙은 없습니다.

건물 처리량만은 게임 데이터 파일에 없어서 [shapez 2 위키](https://shapez2.wiki.gg/)의 건물별 페이지 수치를 썼습니다. 위키가 나열한 5단계 값(예: 절단기 15 / 22.5 / 30 / 37.5 / 45)이 모두 `기준값 × 50/75/100/125/150%`와 정확히 일치해서, 시나리오 파일의 업그레이드 배율과 교차 검증했습니다.

데이터를 다시 뽑으려면 (Python 3.13 필요):

```bash
pip install shapez2==2.1.1
pnpm gen:presets     # 게임 내 목표 도형
pnpm gen:buildings   # 청사진 해석용 건물·플랫폼 메타데이터
pnpm gen:vectors     # 연산 시뮬레이터 테스트 벡터
pnpm gen:blueprints  # 청사진 디코더 테스트 벡터
pnpm gen:progression # 마일스톤·연구 해금 순서
```

**건물 이름은 게임 설치본에서 직접 뽑습니다.** 파이썬 패키지에는 영어 번역만 들어 있어서, 게임의 Unity 애셋에 통째로 박혀 있는 한국어 블록을 읽어옵니다. 게임이 설치돼 있어야 합니다.

```bash
pnpm gen:names       # 건물·플랫폼·색상 한국어 이름
```

마일스톤 이름(`Fluids & Painting` 등)은 압축된 시나리오 번들 안에 있어 아직 못 꺼냅니다. 그래서 그 부분만 영어로 남아 있습니다.

## 검증

- **시뮬레이터 정합성**: 공식 구현으로 생성한 연산 테스트 벡터 **5,000건 전부 일치**. quad/hex 두 설정, 10개 연산 전부 포함.
- **해금 규칙**: 마일스톤별 해금 순서가 게임 데이터와 일치하는지, 그리고 어떤 진행도에서도 **해금되지 않은 건물이 계획에 절대 등장하지 않는지**를 실제 게임 도형 200개 × 5개 시점으로 검증.
- **청사진 디코더**: 실제 플레이어가 공유한 64건물짜리 플랫폼 청사진 + 회전·다중타일 합성 케이스에서 공식 디코더와 **건물 종류·개수·점유 타일 좌표가 전부 일치**.
- **솔버 커버리지**: 게임 내 실제 목표 도형 1,387개 기준

  | 시나리오 | 해결률 | 마일스톤 |
  |----------|--------|----------|
  | 표준 | 97.1% | **100%** |
  | 하드 | 94.4% | 92.7% |
  | 육각 | 98.2% | **100%** |
  | Insane | 76.4% | 79.1% |

  테스트에 최저 커버리지 기준이 걸려 있어서, 솔버를 고치다 커버리지가 떨어지면 CI에서 잡힙니다.

## 솔버가 쓰는 기법

사람이 실제로 쓰는 조립 패턴을 규칙으로 넣고, 성공한 것 중 **실제로 돌리는 데 건물이 가장 적게 드는 계획**을 고릅니다. 비교 기준은 "출력 1개/분당 필요한 건물 대수"라서 목표 처리량과 무관하게 일정합니다.

조각을 깎는 방식도 두 가지를 각각 돌려 보고 싼 쪽을 씁니다.

- **버리기** — 절반 파괴기(40/분)로 필요 없는 반쪽을 버립니다. 건물은 빠르지만 채굴량이 2배 듭니다.
- **양쪽 쓰기** — 절단기(30/분)로 잘라 양쪽을 다 씁니다. 같은 도형에서 깎은 두 조각이 절단기 한 대를 공유해서 채굴량이 절반이 됩니다.

표준 시나리오 369개 도형 기준으로 이 비교를 넣은 뒤 필요 건물이 평균 46.7대 → **42.6대(-9%)**, 추출기는 3,502대 → **2,960대(-15%)** 로 줄었습니다. 해결률은 그대로입니다.

1. **레이어 조립** — 레이어별로 조각을 만들어 아래부터 쌓기
2. **핀 발자국** — 핀 레이어는 위층 전체를 핀 푸셔로 밀어 올린 결과로 복원
3. **노출된 상단 핀** — 레이어 한계(4/5층)에 걸려 위가 잘려 나간 상황을 재현
4. **핀 → 결정체** — 결정체 생성기가 핀을 결정체로 바꾸는 성질 이용
5. **크게 만들고 잘라내기** — 결정체는 빈칸에만 생기므로, 지지대용으로 반대쪽 절반을 채워 만든 뒤 절단
6. **교환기로 반쪽 합치기** — 결정체는 결합 시 부서지므로, 중력이 적용되지 않는 교환기로 좌우를 교환
7. **열 분할** — 서로 겹치지 않는 열끼리 따로 만들어 합치기

## 한계

- 서로 다른 색 결정체가 복잡하게 얽힌 도형, 중간 레이어에 핀이 불규칙하게 박힌 도형 일부는 해법을 찾지 못합니다. 이 경우 **추측 대신 "못 찾았다"고 표시**합니다.
- 계획은 필요 건물 수를 기준으로 고르지만 이론적 최적해를 보장하지는 않습니다. 규칙이 만들어 낸 후보 중에서만 고릅니다.
- 처리량은 이론값입니다. 벨트 분배/합류 손실, 레인 배치, 유체 탱크 병목은 반영하지 않습니다.
- 청사진 뷰어는 읽기 전용입니다. 편집·생성은 지원하지 않고, 구버전 청사진 마이그레이션도 하지 않습니다(모르는 건물은 1칸으로 표시하고 경고합니다).
- 청사진 안의 건물 연결 관계는 해석하지 않아서, 청사진만 보고 처리량을 계산해 주지는 않습니다.
